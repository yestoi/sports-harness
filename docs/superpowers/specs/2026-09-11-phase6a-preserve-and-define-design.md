- **0.4 (§9.5, U8 6A "an epoch label alone does not exclude historical rows") Gate eligibility, built dormant.** `Settings.gate_eligible_from_order_id: int | None = None` and `Settings.gate_eligible_from_run_id: int | None = None`. When both are `None` (the default, and the state this milestone deploys), `harness/report/gate.py` is byte-for-byte unchanged in behaviour: every query keeps `replay = false` and no other filter. When set, every gate query adds `and o.id >= :from_order` (and the signal-side criteria `and s.run_id >= :from_run`): the criteria are module-level `text()` constants dispatched through one fixed signature (`gate.py:638`) and neither entry point sees `Settings` (review I-b1), so the mechanism is one pure function `eligible_sql(sql: str, from_order, from_run) -> str` that returns `sql` unchanged when both are `None` and otherwise inserts the predicates before each constant's `group by`/`order by` (each constant carries a `-- eligibility` marker comment at the insertion point), plus an optional keyword `eligibility: Eligibility | None = None` on `evaluate_gate` and `run_gate` that the CLI fills from the two settings; `gate_reports.criteria_json` records the two values under `eligibility`, and `render_gate` (the gate's own renderer, not `weekly.render_markdown`, which is 6C's file: review I-b2) prints them.
