# Adversarial quality review: Cerebras worker proposal

Reviewed 2026-09-12. Scope: the provisional investigation, CLAUDE.md, autopilot skill and phase/recovery procedures, phase 6A/6C ledgers, and the phase-6 roadmap reconciliation. Research only: no tests, production access, inference calls, configuration changes, or autopilot startup. Findings refer to the reviewed document's current line numbers. Historical ledger statements are evidence of what was recorded, not newly reproduced outcomes.

## Verdict

Proceed only with a narrow experiment, and describe its goal as discovering a safe, faster task class. Do not yet conclude that Astra planning plus strong review preserves quality or that most work can move to Cerebras. The draft already recognizes this uncertainty, keeps the controller/review allocations, and separates worker speed from accepted-change speed. Its remaining gaps concern how the experiment could falsely report success and how policy survives controller improvisation.

## Findings

### Q1 — High: the quality oracle can share the planner's error

**Evidence.** Phase 6A ledger lines 23 and 32–33: the brief carried implementation code, yet that code needed UUID/id corrections, and review subsequently found four Important issues involving cap provenance, a wrong tape bookmark, retained gzip members and missing period CLI coverage. Phase 6C ledger lines 33 and 38: targeted tests and the full suite were reported green, then review found inactive gate variants, inconsistent generated-at timestamps, pooled cross-variant fills and 25,000 full notes documents. Reconciliation lines 18, 25, and 47 explicitly refute a mathematical impossibility claim and an own-side price claim that survived consolidation despite a review correction. Line 49 says replay parity cannot validate an economically wrong model by reproducing itself.

**Risk in the proposal.** Investigation lines 67–69 and 126–130 request independent contracts/tests/review, but independent agents are not necessarily independent evidence. A planner writes the intended behavior, a worker follows it, tests encode it, and a reviewer assesses compliance with it: all four can agree on the same incorrect premise. Front-loading more code can amplify this pattern. Keeping Claude review is necessary for the experiment, but is not a quality equivalence argument.

**Correction.** Separate (1) contract compliance, (2) validity of the contract against governing requirements and actual consumers, and (3) operational/resource validity. Have an evaluator derive a small set of hidden cases directly from authoritative requirements and producer/consumer behavior before seeing the Astra packet or candidate patch. Where useful, include metamorphic/conservation properties and integration probes through real writers/readers. Preserve disputed claims with finding IDs and evidence; a summary must not silently supersede a counterexample. The reviewer should explicitly say when the packet itself is invalid. Such a task counts as a planner/route failure even if both worker arms faithfully implement it.

### Q2 — High: historical replay can leak the solution through the planner, task selection, or repository access

**Evidence.** Investigation lines 126–128 correctly prohibit showing later fixes/reviews/expected patches to the implementer, but the same research session has already read these exact failures and proposes generating Astra packets. Phase 6C ledger line 37 records that a brief-verbatim test imported another task's new module despite `Depends on: none`. The 6A phantom criterion discovery (ledger lines 46–48) is now known and could easily be supplied to Cerebras as an apparently original acceptance case. A worktree at an old SHA normally retains access to the shared Git history; simply checking out the base does not make a historical benchmark blind.

**Risk.** An original-brief Claude arm compared with a hindsight-informed Astra arm credits oracle knowledge as planning improvement. Even B versus C/D then establishes only performance on unusually complete, retrospectively repaired packets. Holding fixes out from the implementer does not repair planner contamination. A historical task requiring edits to a ready-made code block mostly measures transcription.

**Correction.** Label current-session historical packets as hindsight-assisted calibration. Do not use them to estimate prospective Astra benefits. For a fair replay, isolate both planner and worker from post-cutoff transcripts, reviews, branches, Git objects, caches, sibling checkouts and answer-bearing network paths; source packets only from material actually available at the original time. The practical next validation should include freshly selected prospective tasks, packets frozen before implementation and hidden cases frozen before seeing candidates. Record packet provenance and any hindsight additions. Keep known difficult historical bugs as separate challenge cases, not as representative low-risk production work.

### Q3 — High: 12–20 tasks cannot establish the desired quality claim; survivor and reviewer-repair bias can make even screening misleading

**Evidence.** Investigation line 132 candidly calls the threshold screening rather than statistical equivalence, but leaves the later non-inferiority design unspecified. Current phase procedure lines 24–30 allows reviewers to fix Minors themselves and routes small scoped rereviews to Haiku. Phase 6C ledger line 80 labels a provenance-bullet position issue Important while accepting it unchanged; severity labels therefore need adjudication before counting. Several historical tasks returned DONE_WITH_CONCERNS or required substantial fixes, so accepted-only samples exclude meaningful routing failures.

**Risk.** The stronger reviewer can silently repair poor patches, producing equal final defect counts but worse dependency on review and worse risk when the reviewer misses something. An aggregate median hides a slow/unsafe task class or repeated escalations. No observed escape is weak evidence of a low escape rate: if n independent tasks each have zero observed escapes, the one-sided 95% binomial upper bound is `1 - 0.05^(1/n)`, about 22.1% for 12 and 13.9% for 20. Correlated tasks make even that idealized interpretation optimistic. This calculation is not a comparison to Claude and does not establish non-inferiority.

**Correction.** Freeze an independent severity rubric, defect denominator, target task population, comparator and non-inferiority margin before evaluation. Record the reviewer's original verdict and every reviewer edit before repair; keep a final post-repair acceptance metric too. Include every dispatched task in route-level elapsed time/cost, including rejects, timeouts and escalations; separately report first-pass success. Group related tasks by dependency/feature so repeated near-identical tasks do not become false independent evidence. Use paired/interleaved arms, distributions and explicit uncertainty, not only the median. A small pilot can rule out obvious regressions and justify more measurement; it cannot certify equal quality or justify moving most work.

### Q4 — High: task labels and fixed file lists are unreliable admission rules

**Evidence.** Phase 6C preflight declared no additional conflicts (ledger line 19), but line 37 later found the undeclared module dependency. Phase 6A line 47 extended Files to a dashboard consumer after a new metadata key would create a phantom criterion. Phase 6C lines 59–60 needed a real writer/matcher agreement test and an EXPLAIN check; the controller explicitly admitted that planner settings pin an index-path shape, not the production planner's choice. Reconciliation line 53 identifies multiple distant Chicago-week consumers, so even the proposed 'small pure helper' can participate in sensitive reporting semantics.

**Risk.** The draft rightly routes by uncertainty and impact, but its candidate row ('fixture builder', 'CLI wiring', 'small pure helper') can still become a size-based whitelist. Routing errors matter as much as worker errors. A model confidently following an incomplete packet may never emit NEEDS_CONTEXT. A test-only fixture can encode the wrong semantic truth.

**Correction.** Require positive admission evidence: known consumers/producers, stable semantics, bounded data/resource behavior, meaningful trusted acceptance checks, and no unresolved dependency. Missing evidence routes to Claude. Treat fixtures/tests for order identity, research validity, gate criteria or settlement as sensitive regardless of filename. When a worker discovers a new import, changed schema reader, scope expansion or changed premise, invalidate the packet and reevaluate scheduling and review allocation; do not merely let it edit more files. Include deliberately misclassified cases in the offline experiment and measure the controller's routing/escalation accuracy. Report what fraction of real ready work qualifies; without this denominator there is no basis for the 'most tasks' ambition.

### Q5 — High: documented gates have already been overridden; a worker wrapper must enforce controller transitions and stale attempts

**Evidence.** Phase 6A ledger line 38 explicitly reports four implementer slots against a ceiling of three and rules a docs-only exception acceptable. Phase 6A lines 26 and 35 accept earlier full-suite evidence plus targeted fixes for merge; current phase procedure lines 35–36 require a full suite on the branch before merge. Recovery procedure lines 16–31 correctly says workers may survive compaction, a PID alone is not liveness, partial work must survive, and retries/counters must not reset. Draft wrapper lines 79–89 calls for leases/heartbeats and evidence bound to SHA but does not specify stale lease fencing or legal state transitions.

**Risk.** A prompt-based controller may override the experiment's constraints under deadline pressure just as a ledger records the prior slot exception. A timed-out old worker can finish after a retry, consuming resources or producing a result that appears current. Persisted state without a fencing rule is insufficient. Exact SHA binding alone also fails if a supposedly accepted worker/test process can still modify its worktree or writable test inputs.

**Correction.** Make resource acquisition, allowed-path changes, admission, evidence verification, retry accounting and integration authorization checks executable outside the LLM. Use attempt IDs and lease generations; accept results only for the current attempt and packet/base, and reject stale results. Before retry or cleanup, reconcile/stop the prior process group or leave it quarantined with ownership preserved; never reuse its checkout concurrently. Verify the candidate has stopped mutating, capture its immutable tree and trusted test environment/config identifiers, and invalidate acceptance on relevant changes. Exercise crash points in an eventual wrapper test: after dispatch but before checkpoint, result written before controller receipt, lease expiry while tools still run, and controller restart while tests own the semaphore. Keep this finite and local, not a platform rewrite.

### Q6 — Medium: stronger review can become the new bottleneck, and the proposed first experiment is larger than needed

**Evidence.** Investigation lines 109–111 correctly includes review, tests, repair and integration outside accelerated inference. The historical examples above show real reviewer work even with Sonnet implementations and supplied code. Four arms across 12–20 tasks plus two Cerebras models, an improved dispatcher and canary can consume substantial setup/evaluation before proving a worker substitution is promising.

**Correction.** Start with B versus one C candidate under the same compact packet, runner, trusted evaluation and review policy. Instrument the current recovered controller separately. Add the second Cerebras model if the first shows a repair/quality tradeoff worth comparing. Measure ready-task-to-final-acceptance time and total reviewer/controller work, not just inference or implementer duration. Bound the review backlog/WIP; generating patches faster than review capacity can increase task lead time. A/B harness attribution and controller comparisons can follow only if the basic worker swap survives the feasibility screen.

## Strongest case against adopting Cerebras here

The historical bottleneck may be incomplete semantics, late discovery of cross-system dependencies, constrained tests and integration rather than token generation. The highest-value historical fixes involve sequence scope, recovery watermarks, side identity, sample validity, metadata consumers and query behavior. These remain strong-model work under the proposed policy. Once those are excluded, the eligible remainder may be small and often better executed by scripts. Astra packets, an external runtime, isolation, independent review and occasional Claude repairs could add more critical-path work than fast decoding removes. Current sessions also predate a just-adopted context recovery improvement, so a cheaper/faster baseline may already be available without provider substitution. There is no empirical evidence in these files that GPT OSS or Qwen matches Sonnet on this project's eligible tasks, nor evidence that 'most tasks' are eligible. The strongest defensible recommendation is therefore to retain the Claude loop until a measured, narrow worker substitution wins.

## Preferred smallest experiment

1. During the next otherwise-authorized development work, capture baseline timestamps without changing model allocation. Select six genuinely upcoming, independent, bounded tasks in a single proposed eligible class. Add two hidden-dependency/semantic challenge cases as separate offline routing probes. Six is a feasibility screen, not a quality sample.
2. Freeze one Astra packet per task and an independently derived acceptance/evaluation record before candidate implementations exist. Charge packet/evaluation preparation time. Original historical tasks already read by this investigator may be used only for explicitly labeled hindsight-assisted calibration.
3. Run paired Claude and one Cerebras candidate from identical immutable inputs, isolated environments, pinned settings and the same resource schedule. Keep all work off production, one test suite at a time, with no live autopilot authority. The controller/reviewer policy remains fixed; record original reviewer findings before any reviewer repairs.
4. Include the permitted bounded repair and Claude escalation in each route's time and cost. Accept nothing based solely on a worker statement. Record first-pass/after-review defects, planner/packet defects, routing failures, review effort, total elapsed time and failures/abstentions for every dispatched task.
5. Stop expansion on a substantive semantic miss, instruction-containment failure, evidence mismatch, stale-attempt acceptance or task-class misroute. A clean, faster screen licenses a larger prospective non-inferiority study for that class, not a claim of equal quality and not majority routing. A failed speed screen licenses keeping compact packets and the Claude baseline.
