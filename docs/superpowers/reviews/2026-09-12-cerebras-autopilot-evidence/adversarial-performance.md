# Adversarial review: Cerebras autopilot performance

Reviewed 2026-09-12. Scope: read-only project inspection and official documentation; no inference, tests, operational tools, configuration changes or production access. The recommendation is a reasonable hypothesis, not evidence that this project's accepted output will accelerate. I would reject routing most tasks today and approve only a staged feasibility experiment after its setup is authorized.

## Findings

1. **High — The proposed B/C comparison confounds the model with its agent runtime.** Investigation lines 77–79 use normal Claude subagents and an external OpenCode/Aider worker; lines 122–126 claim B versus C/D isolates worker substitution. Different editing tools, system prompts, context compaction, retry policies and tool latencies change results even with identical task packets. **Correction:** describe B/C as a comparison of operational worker stacks, which directly answers the user's practical question. Pin runner/provider-adapter versions and capture their settings. If attributing gains to Cerebras/model inference matters, add a same-runner Claude arm, while accounting separately for its API spend. Do not silently equate native Claude subscription use with Claude through an external runner. This is a design inference, not a measured confound effect.

2. **High — Historical replay needs stronger exclusion of future information than a base-commit worktree.** Investigation lines 83 and 119–126 propose worktrees at historical bases while forbidding later code/reviews. `scripts/worktree.sh:12–14` uses Git worktrees and links the controller environment. A historical worktree shares the repository's Git object store; checkout date does not prevent reading future patches through Git. Current task packets written from later findings can also leak the answer. **Correction:** use a sanitized source snapshot in a fresh repository, with no future objects, remotes, review artifacts or shared home/session history. Prepare implementation packets only from contemporaneously available requirements; keep later discoveries in evaluator material. This is a concrete feasibility gap, not an assertion that a worker has cheated.

3. **High — Isolation is correctly required, but the existing test topology does not implement it.** `scripts/worktree.sh:14` links `$ROOT/.venv`; `Makefile:155` can fall back to the controller environment. `scripts/testdb.py:11–21` gives all branches the same database-creation identity and tests connect with that identity. A per-branch database name is not a database privilege boundary. Current state line 21 records shared test-server blocking and the two-suite ceiling. **Correction:** before unattended execution, specify a concrete isolated process/filesystem environment, independent immutable dependencies, and a trusted test broker that provisions job resources without handing workers shared administrative credentials. Preserve `make test` through a deliberately designed local test endpoint; a separate network namespace makes the host's localhost unavailable unless that route is explicitly provided. Include the cost and memory of this isolation in the benchmark. For an early feasibility run, avoid building a general dispatcher: one externally supervised isolated job is sufficient. Actual DB role privileges were not queried.

4. **Medium — Prompt throughput can dominate even the draft's compact example.** The draft prices 400k input plus 40k completion/reasoning tokens per task (line 113). [Cerebras rate limits](https://inference-docs.cerebras.ai/support/rate-limits) list Qwen PayGo at 150k uncached/450k total TPM; admission reserves prompt plus estimated completion tokens. For fully uncached requests, 440k tokens represent **176 seconds of sustained quota**, versus about 22 seconds to decode 40k at the advertised 1,850 tok/s. This is a quota arithmetic illustration, not predicted task latency: initial bucket capacity, cache hits and interleaved tool execution change individual runs. The same arithmetic is 26.4 seconds at 1M uncached TPM for GPT OSS, or 52.8 seconds at the conflicting 500k published limit. **Correction:** log prompt/cache/completion tokens, reservations, time to first token, throttle waits and actual completion time. Do not evaluate speed on the free trial: its 5 RPM and 30k uncached TPM constrain normal agent requests. Check actual paid-account limits before drawing throughput conclusions.

5. **Medium — Official integration documentation establishes a route, not a working versioned stack.** [Cerebras/OpenCode](https://inference-docs.cerebras.ai/integrations/opencode) currently lists GPT OSS and Gemma 4 in its available-model table, while the [public catalog](https://inference-docs.cerebras.ai/models/overview) lists GPT OSS and Qwen 3.8. The draft already correctly records other catalog/API discrepancies. [API version documentation](https://inference-docs.cerebras.ai/api-reference/versions) confirms v2 validation is now default while the URL remains `/v1/chat/completions`. **Correction:** make a single model-selection plus multi-turn tool-call smoke test the first inference experiment, including truncation and tool-result pairing; record exact model ID and adapter version. Do not spend time on a custom runtime before this passes. [OpenCode permissions](https://opencode.ai/docs/permissions/) also document permissive defaults and auto approval; these settings do not replace the isolation required above.

6. **Medium — The initial experiment is larger than necessary and omits an explicit amortization decision.** Twelve to twenty tasks across four arms is 48–80 implementations before repeated runs, reviews, repairs and canaries. The draft correctly charges packet preparation but does not explicitly include implementation/maintenance time for the dispatcher, isolation, telemetry and evaluator. **Correction:** first reconstruct critical-path time for three recent accepted bounded tasks, and document a break-even inequality: `expected remaining eligible tasks × net minutes saved per task > setup and maintenance minutes`. Then run a feasibility screen on one mechanical task, one bounded code task and one deceptive small semantic task, using an existing runner. Expand to the larger evaluation only if end-to-end evidence warrants it. The three-task screen is not a quality claim or authorization for live routing.

7. **Medium — Project-wide acceleration needs eligible-work coverage, not only faster median eligible tasks.** The routing table leaves production diagnosis, sensitive semantics, integration and strong review on Claude. `.claude/skills/autopilot/references/phase.md:35–36` requires full suites before merges and deployments; state lines 4–12 show operational resource failures and calendar-dependent work. The phase 5 ledger lines 29–33 records six-minute database-drop blocking and checkpoint contention. These are historical records, not freshly reproduced timings. **Correction:** measure the share of milestone critical-path time spent in the inference actually eligible for replacement, and report accepted milestone lead time alongside task medians. A 25% gain on a small task class may not satisfy the user's desire to get the project done much faster. Do not invent a numerical project-wide gain from historical token totals.

## Strongest case against the proposal

The current system already assigns mechanical tasks to Haiku and ordinary implementation to Sonnet, keeps three implementers active, and requires expensive independent reviews and full suites. Historical failures are substantially semantic, cross-consumer and operational. The easiest edits may already be cheap, parallel, or scriptable; the slowest remaining work may be precisely what cannot safely be routed down. A new runtime adds packet preparation, credential/isolation work, context limits and repair opportunities while preserving the serial acceptance bottlenecks. A measured critical path dominated by tests, reviewers and operational waits would make Cerebras a faster draft generator with little or negative effect on accepted milestone throughput. This is the strongest plausible alternative explanation, not a proved outcome.

## Preferred smallest next step

Produce a timestamped, critical-path breakdown for three recent accepted bounded tasks using existing transcripts and ledgers, plus one sanitized historical task packet with private evaluator checks. Set a setup-time budget and identify an existing runner/version. Only then, under a separately authorized inference/setup experiment, smoke-test one paid-account Cerebras worker and run the three-task feasibility screen with the current controller/review gates. No durable multi-provider service, controller change or broad routing is needed to answer this first question.
