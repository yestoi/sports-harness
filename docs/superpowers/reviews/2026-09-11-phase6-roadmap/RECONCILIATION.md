**Evidence behind the corrections that change implementation order.**

The sequence mismatch is visible at [book.py:56](/Users/trey/dev/sports/harness/execution/book.py:56) and [book.py:272](/Users/trey/dev/sports/harness/execution/book.py:272), versus the subscription-level recorder at [ws_sink.py:84](/Users/trey/dev/sports/harness/recorder/ws_sink.py:84). Our saved tape contains sid 2 sequence 50604–50615 without a gap, interleaved among several tickers. Quiet markets are one possible invalidation cause; they do not explain away this structural error. Similarly, zero recorded gap rows cannot prove every reconnect or failed write preserved complete tape.

The new recovery reproduction exercises [loop.py:828](/Users/trey/dev/sports/harness/execution/loop.py:828). Starting with five contracts ahead, a three-contract trade during a dirty interval and a recovery snapshot containing only two ahead should produce no additional fill from that historical trade. Advancing only the delta cursor leaves the trade eligible against the already-reduced queue and produces a spurious one-contract fill. These are trades already represented in the recovery snapshot, not necessarily trades the simulator had previously consumed. [Execution probes](evidence/execution-reconciliation-probes.py) and [captured output](evidence/execution-reconciliation-output.txt) preserve this distinction.

Order 157's recorded final values—fills of 25 and 13.92, total traded-at-price 63.92, queue remaining zero—do not uniquely identify its mechanism. A synthetic initial queue of 6,401, a same-time decrement of 6,376, and prints of 25, 25 and 13.92 produce the same values without recovery. This does not establish that either synthetic path is what happened live. The defensible status is “requires tape audit,” not “proven fake” or “proven valid.”

**Infrastructure conclusions we should retain, and limits we should state.**

The other field record's `/volume1 → LVM → md1 → sda` mapping supports rotational database storage. It does not benchmark an alternative machine. Our earlier recommendation should be sharpened to “prepare dedicated compute and fast local database storage; select the actual target after inventory and rehearsal.” Fixing false dirty books will activate work previously skipped, so the current broken workload is a poor sizing benchmark. CPU/concurrency can matter even when I/O wait is low; no single host metric proves an upgrade cannot help.

The backup exclusions are explicit at [backups.md:3](/Users/trey/dev/sports/docs/runbooks/backups.md:3). Some `_legacy` children may not match the same patterns as `_y*` partitions, so neither “full backup” nor an exact omitted-size estimate should be assumed. PostgreSQL documents that a logical dump is a consistent snapshot at the start of the dump and is suitable for transfer between architectures; writes after that snapshot need a separately defined transfer boundary. [PostgreSQL SQL dump documentation](https://www.postgresql.org/docs/16/backup-dump.html).

No supplied evidence requires disabling FileVault, an external 2 TB disk, a particular RAM minimum, a particular parallel dump/restore worker count, or a whole-weekend migration ban. Define restart behavior, storage runway, backup coverage, measured resource headroom and rollback requirements, then select the implementation. Tuesday 08:00–16:00 also overlaps the existing futures cron, so it is only a candidate window, subject to game and job checks. The free-space guard is real; an early-October deadline from rounded `df` values and a short growth estimate is not. Copying the database while retaining the source does not immediately free NAS space.
