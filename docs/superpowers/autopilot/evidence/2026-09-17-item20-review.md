## Defects in the draft brief (soundness reviewer; verified in code unless noted)

1. Guard and incremental read are two statements under READ COMMITTED: a late below-max row
   committed before the guard plus a head row committed between the statements reconciles the
   count and silently drops a print. Make it one statement (scalar subqueries for count/min/max
   plus the tail rows), fall back on anything else.
2. "Insert-only" is incomplete: `harness/normalize/runner.py:355` deletes `source='rest'` rows on
   reprocess, and the retention proposal (rows 72-73) drops partitions the current window sits in.
   Serve the cache only when count AND min(ts) AND max(ts) match.
3. Cache built `TapePrint`s (pre-dedupe list plus deduped output), not raw rows; otherwise most of
   the cost survives. Never hand out the cache object itself (`has_print` scans it).
4. Append `venue` to the ORDER BY (PK is (venue, trade_id, ts); `ix_trades_venue_trade_id` is
   non-unique) or assert single venue.
5. Hard total-row cap with full-read fallback, trim below `lower`, a cached-rows gauge; estimate
   ~60 MB now, 265-320 MB at 500k rows; there is no `exec.rss_mb`.
6. `_is_statement_timeout` shrinks `_delta_batch` for any timeout in the block; a guard timeout
   must not.
7. Tests owed: second-connection race test, 200-loop randomized identity fuzz, delete/partition
   fallback, aliasing, `lower` later-then-earlier, row-cap bound, `at is not None` with replay false.
8. Blast radius of a wrong cache: silently missing fills in `fills`, `ledger`, `orders` nw_ columns,
   `order_events`; no live check catches an under-fill; corrections are new rows only (§0.12).
   Reviewer's odds of clean-by-14:00: 45-55 % as drafted, 65-70 % amended.
